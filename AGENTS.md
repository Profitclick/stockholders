# AGENTS.md

- `src/lib/custodyPlatforms.ts` is the single source of truth for mapping registered shareholder names to custody/broker platforms; the ETL and UI both import it — why: one classifier avoids drift between data load and display.
- Platform exposure is computed offline with DuckDB by `scripts/etl/platform-exposure.ts` and bulk-loaded through the admin-only `platform-load` edge function (history 2022+ via `--first`); platform tables are read-only for the app — why: millions of register rows must not go through the browser, and person-level data must not be publicly writable.
- AI ownership Q&A (`ownership-ask` edge function) only sends the model aggregates built by the admin-gated SQL function `ownership_ai_context`; never pass person-level rows or names to the model — why: privacy, the model cannot leak what it never sees.
- Multi-year person ownership history lives in `person_ownership_history` (one row per person+company, pct/shares per year, trend); it is built offline with DuckDB from the yearly register Parquet files and bulk-loaded through the admin-only `holdings-load` edge function; prefix search goes through the security-definer `search_ownership_history` RPC because LIKE under RLS cannot use indexes — why: millions of rows must not pass through the browser and the table stays read-only for the app.
- Named company owner histories use admin-RLS security-invoker views and bounded stable company pagination; all-period person signals are preaggregated in `historical_ownership_signals` and refreshed after offline loads with the admin-gated refresh RPC — why: full historical criteria must not require sending millions of person rows to the browser, and register movements must not be misrepresented as trades or capital issues.
- Annual platform tables reuse the selected company's holdings and derive loaded-year availability from platform statistics; named person year tables filter existing history server-side — why: year comparison must stay lightweight and never invent values for unloaded years.
